Дослідницько-інженерний проєкт із вивчення просторово-часової динаміки повітряних тривог у 24 областях України (березень 2022 – жовтень 2026 рр.) та короткострокового прогнозування початку нової тривоги у спокійні години на горизонті $[T, T + 1\text{h})$. Усі гіпотези перевірено паралельно на **двох незалежних корпусах даних** — офіційному (`official_data_uk.csv`) та волонтерському (`volunteer_data_uk.csv`).

## ⚡ Executive Summary (Ключові висновки дослідження)

1. **Етап 1 — Стабільна просторово-часова структура між двома незалежними джерелами (RQ1–RQ3):**
   * **Циклічність (RQ1):** підтверджено статистично значущий тижневий ритм (тест Краскела-Волліса $H = 25.52, \ p = 2.74 \times 10^{-4}$ на Official; $H = 21.66, \ p = 0.0014$ на Volunteer) із піком у середу–п'ятницю та мінімумом у неділю, а також стабільну частку нічних стартів (`00:00–05:59 Europe/Kyiv`: **$20.2\% – 24.0\%$** за роками).
   * **Кластеризація областей (RQ2):** ізольована кластеризація на навчальному періоді `Train <= 2024-04-30` для ML-ознак (`low_activity`, `medium_activity`, `high_activity`) показує високу узгодженість між джерелами, а описова кластеризація за весь період чітко виділяє 3 географічні пояси (Глибокий тил, Транзитний Центр і Південь, Прифронтова/Прикордонна зона).
   * **Просторові коридори поширення (RQ3):** крос-кореляції на 10-хвилинній сітці для 49 пар сусідніх областей демонструють високу міжджерельну відтворюваність ($\rho_{\text{Spearman}} = 0.960$ між Official і Volunteer) і фіксують стійкі лаги поширення у 10–20 хвилин вздовж південних, східних і центральних маршрутів.
2. **Етап 2 (Блок А) — Статичне ML-моделювання та діагностика 5-кратного зсуву розподілу ознак:**
   * За формальним передреєстрованим правилом ($\arg\max \text{PR-AUC}$ на Validation `2024-05-01` – `2025-05-31`) переможцем серед кандидатів (`Baselines 1–3`, `LogReg A/B/C`, `LightGBM A/B/C`) обрано **`LightGBM (Set C: Spatial + Adaptive, 22 ознаки)`** (`Val PR-AUC = 0.3012` на Official; `0.3107` на Volunteer `naive_as_is` / `0.3116` на `naive_fixed_D`).
   * На повному Test (`2025-06` – `2026-09`) заморожений статичний `LightGBM (Set C)` на Official перевершує `Adaptive 14-day Baseline` ($\Delta\text{PR-AUC} = +0.0297 \ [+0.0220, +0.0373]$, $\Delta F_2 = +0.0249 \ [+0.0189, +0.0304]$), проте поступається простішому пост-хок набору `Set B` (13 ознак без історичних і національних агрегатів: `PR-AUC = 0.3741` проти `0.3329`).
   * **Причина просідання статичного `Set C`:** між `Train` (`2022–04.2024`) і `Test` (`2025-06..2026`) середня кількість одночасно активних областей `national_active_count` зросла у **$4.73\times$** на Official (`1.17` $\to$ `5.55`) та у **$4.95\times$** на незалежному Volunteer (`1.12` $\to$ `5.57`), де не було серпневої реформи логування 2025 року. Дерева рішень статичного бустингу, заморожені на даних 2022–2024 рр., екстраполюють із застарілими порогами розбиття.
3. **Етап 2 (Блок Б) — Чутливість до політики `naive` на Volunteer та помісячний Walk-Forward Retraining:**
   * Перевірка трьох строго каузальних політик обробки прапорця `naive` у волонтерських даних (`naive_as_is`, `drop_naive`, `naive_fixed_D` із медіаною тривалості $D_{\text{oblast}}$ строго з `Train`) підтвердила повну інваріантність висновків.
   * Перехід до **помісячного донавчання (`LightGBM Set C [WF Rolling 12m]`, 12m Train + 2m Val з 2-годинним буфером `embargo`)** радикально покращує якість бустингу:
     * **Official:** Pooled `PR-AUC` зростає з `0.3329` (Static) до **`0.4203 [0.409, 0.431]`** ($\Delta_{\text{vs Adapt}} = +0.1171 \ [+0.1081, +0.1261]$, $\Delta_{\text{WF − Static}} = +0.0873 \ [+0.0789, +0.0954]$, виграш у `16/16` місяців), а на останніх 60 днях — з `0.3809` до **`0.5139 [0.488, 0.541]`** ($\Delta_{\text{vs Adapt}} = +0.1450 \ [+0.1177, +0.1726]$). При цьому повний набір `Set C` у режимі Walk-Forward впевнено перемагає скорочені набори `Set B` (`0.3914`) та `Set C'` (`0.3985`).
     * **Volunteer (`naive_fixed_D`):** `LightGBM (Set C) [WF Rolling 12m]` статистично значуще перемагає `Adaptive 14-day` як на повному Test (`0.4050 [0.397, 0.413]` проти `0.3924`, $\Delta_{\text{vs Adapt}} = +0.0128 \ [+0.0082, +0.0168]$, $\Delta_{\text{WF − Static}} = +0.0147 \ [+0.0110, +0.0180]$, виграш у `15/17` місяців), так і на останніх 60 днях (`0.4975 [0.486, 0.512]` проти `0.4810`, $\Delta_{\text{vs Adapt}} = +0.0167 \ [+0.0089, +0.0252]$).
     * **⚠️ Важливе застереження для Volunteer:** на волонтерському датасеті `LightGBM (Set C) [WF Rolling 12m]` **не є безумовно найкращою моделлю за всіма метриками** — за `PR-AUC` він трохи поступається статичній лінійній моделі `LogReg (Set C) [Static Initial Train]` (`0.4050` проти `0.4097` на повному Test, $\Delta = -0.0046 \ [-0.0081, -0.0013]$; `0.4975` проти `0.5002` на останніх 60 днях, $\Delta = -0.0027 \ [-0.0073, +0.0028]$), переважаючи її лише за пороговою метрикою $F_2$-Score ($\Delta F_2 = +0.0064 \ [+0.0044, +0.0083]$) та калібруванням імовірностей (`Brier = 0.1093` проти `0.2645`).

### Чому в таблиці Test Official рівно `197 083` рядки, а у зрізі з квітня 2025 року — `228 371`?
Це ключова деталь архітектури Feature Store та протоколу Walk-Forward:
* У матриці ознак [`data/processed/ml_features_hourly.parquet`](data/processed/ml_features_hourly.parquet) колонка `split_set` ділить спокійні години (`797 428` рядків) на три хронологічні частини з 2-годинним буфером `embargo` на межах:
  * **`Train` (`split_set == "train"`, `2022-03-15` – `2024-04-30`):** `410 150` спокійних годин (`33 240` стартів, базова частка **$8.10\%$**).
  * **`Validation` (`split_set == "val"`, `2024-05-01` – `2025-05-31`):** `190 195` спокійних годин (`19 342` старти, базова частка **$10.17\%$**).
  * **`Test` (`split_set == "test"`, `2025-06-01` – `2026-09-07`):** рівно **`197 083`** спокійні години (`20 250` стартів, базова частка **$10.27\%$**).
* Коли запускається помісячний протокол `Walk-Forward Retraining` ([`src/models/run_walk_forward_experiment.py`](src/models/run_walk_forward_experiment.py)), для першого тестового місяця `2025-06` йому потрібне 2-місячне внутрішнє валідаційне вікно `Val_M` (`2025-04-01` – `2025-05-31`, з 2-годинним `embargo`), яке містить рівно **`31 288`** спокійних годин із `split_set == "val"`.
* Таким чином:
  $$\underbrace{31\,288}_{\text{квітень–травень 2025 (внутрішній Val}_M\text{)}} + \underbrace{197\,083}_{\text{офіційний Test (з 2025-06-01)}} = 228\,371\text{ рядок.}$$
* **Яка цифра є правильною у фінальних таблицях і OOF-файлі?** І у фінальних таблицях (`ml_models_benchmark.csv`, `walk_forward_overall_benchmark.csv`), і у збереженому файлі позавибіркових прогнозів [`data/processed/walk_forward_oof_predictions_official.parquet`](data/processed/walk_forward_oof_predictions_official.parquet) міститься рівно **`197 083` рядки** — виключно тестовий період `split_set == "test"` від `2025-06-01 00:00 UTC` (відповідно на Volunteer `naive_fixed_D` у [`walk_forward_oof_predictions_volunteer_fixed_d.parquet`](data/processed/walk_forward_oof_predictions_volunteer_fixed_d.parquet) — рівно **`256 490` рядків** `split_set == "test"`).

## 🔬 2. Етап 1: Описова аналітика просторово-часових закономірностей (RQ1–RQ3)

Усі три дослідницькі питання першого етапу перевірені паралельно на Official (`84 907` інтервалів по 24 областях) та Volunteer (`113 525` інтервалів у `naive_as_is`; `108 576` на спільному часовому вікні до `2026-09-07`).

### 2.1. Часова циклічність та тривалість тривог (RQ1)
* **Тижневий ритм (тест Краскела-Волліса):**
  * **Official:** $H = 25.52, \ p = 2.74 \times 10^{-4}$ (3 статистично значущі пари днів після поправки Бонферроні $\alpha_{\text{adj}} = 0.00238$). Пік — середа–п'ятниця (медіана 52–53 об'єднаних обласних тривог на добу, середнє 53.4–55.0), мінімум — неділя (медіана 47, середнє 46.8 тривог/добу).
  * **Volunteer:** $H = 21.66, \ p = 0.0014$, аналогічне зростання активності у середині робочого тижня та спад у неділю.
* **Добовий профіль та нічні тривоги (`00:00–05:59 Europe/Kyiv`):** після коректної агрегації порайонних тривог у 2025–2026 роках частка тривог, що починаються вночі, залишається стабільною в діапазоні **$20.2\% – 24.0\%$** за роками (2022: $24.0\%$, 2023: $21.5\%$, 2024: $20.2\%$, 2025: $20.5\%$, 2026: $22.9\%$).
* **Порівняння тривалостей між джерелами (`reports/comparison/official_vs_volunteer_comparison.csv`):** на спільному вікні `2022-03-15 .. 2026-09-07` медіанна тривалість на Official становить **43.15 хв** (середнє **102.40 хв**), тоді як на Volunteer — **30.68 хв** (середнє **49.06 хв**), оскільки після серпня 2025 р. об'єднання всіх районів області на Official утворює довші неперервні обласні інтервали, всередині яких на Volunteer фіксується кілька коротших хвиль ($64.5\%$ стартів Volunteer після грудня 2025 р. припадають всередину вже відкритого інтервалу Official).

### 3.1. Постановка задачі, ієрархія наборів ознак та формальне правило вибору на Validation
* **Одиниця прогнозу $(T, \text{oblast})$:** регулярна годинна сітка в UTC (`timestamp_utc`), кондиціонована на стан спокою (`is_active_T == 0`).
* **Цільова змінна (`target_onset_next_1h`):** $y_T = 1$, якщо нова тривога в області починається у піввідкритому інтервалі **$[T, T + 1\text{h})$**.
* **Ієрархія наборів ознак (усі обчислюються строго з даних до моменту $T$, `closed="left"`, на повній годинній сітці до фільтрації спокою):**
  * **Набір A (Time, Burden & Train Cluster — 10 ознак):** `hour_sin`, `hour_cos`, `day_of_week`, `is_weekend`, `month` (за `Europe/Kyiv`), `burden_last_6h`, `burden_last_24h` (частка активних годин у $[T-6\text{h}, T)$ та $[T-24\text{h}, T)$), та One-Hot індикатори кластера з Train (`cluster_1_low_activity`, `cluster_2_medium_activity`, `cluster_3_high_activity`).
  * **Набір B (A + Spatial at $T$ — 13 ознак):** Набір A + миттєвий стан сусідніх областей рівно в момент $T$: `neighbors_active_count`, `neighbor_any_active`, `neighbor_active_ratio`.
  * **Набір C (B + Adaptive & Spatio-Temporal Memory — 22 ознаки, основна передреєстрована конфігурація):** Набір B + 9 адаптивних та просторово-часових ознак: `adaptive_rate_7d/14d/30d`, `national_active_count`, `onsets_last_24h`, `hours_since_last_alert` (`clip(upper=720.0)`), `neighbors_active_lag_1h/2h/3h`.
  * **Набір C' (`FEATURE_SET_C_PRIME`: B + Adaptive & Neighbor Lags Only — 19 ознак, пост-хок експеримент):** Набір C без трьох найбільш чутливих до зсуву розподілу ознак (`national_active_count`, `hours_since_last_alert`, `onsets_last_24h`).
  * **Набір D (`FEATURE_SET_D_ASTRO`: Set C + 8 детермінованих астрономічних і календарних ознак — 30 ознак, пост-хок exploratory у блоці Walk-Forward):** Набір C + висота Сонця (`solar_altitude_deg`), цивільна/навігаційна ніч (`is_night_civil`, `is_twilight_nav`), години до світанку/заходу, освітленість Місяця та річні гармоніки `day_of_year_sin/cos`.
* **Формальне правило вибору переможця на Validation (`reports/official/val_evaluation_details.json`):**
  * Заздалегідь визначене правило вибору основної моделі: $\arg\max \text{PR-AUC}$ на вибірці Validation (`2024-05-01` – `2025-05-31`) серед передреєстрованих кандидатів (`Baselines 1–3`, `LogReg A/B/C`, `LightGBM A/B/C`).
  * Переможець на Validation: **`LightGBM (Set C: Spatial + Adaptive)`** як на Official (`Val PR-AUC = 0.3012 [0.289, 0.314]`, `Val F2 = 0.4910 [0.479, 0.502]`), так і на Volunteer (`Val PR-AUC = 0.3107 [0.299, 0.323]` у `naive_as_is` та `0.3116 [0.300, 0.324]` у `naive_fixed_D`).
  * Усі висновки про перевагу статичного `Set B` за PR-AUC та конструювання `Set C'` зроблені **після перегляду результатів на Test і є пост-хок (`post-hoc`)**.

## 🔄 4. Етап 2 (Блок Б): Помісячне донавчання (Monthly Walk-Forward Retraining)

### 4.1. Каузальний протокол Walk-Forward (`src/models/run_walk_forward_experiment.py`)
Щоб перевірити, як періодичне оновлення дерев рішень адаптує модель до нового режиму тривог у 2025–2026 рр., реалізовано помісячний протокол `Walk-Forward Retraining`:
* **Крок переоцінки:** кожен календарний місяць $M$ тестової вибірки, починаючи з `2025-06` (`16` тестових місяців `2025-06..2026-09` на Official; `17` тестових місяців `2025-06..2026-10` на Volunteer `naive_fixed_D`).
* **Вікно навчання та внутрішньої валідації перед місяцем $M$:**
  * `WF Rolling 12m`: 12 календарних місяців навчання `Train_M` + 2 останні місяці перед $M$ як `Val_M` (для `early_stopping(30)` у LightGBM та вибору порогу $p^*_M = \arg\max F_2(\text{Val}_M)$).
  * `WF Expanding`: вся історія від березня 2022 р. до початку `Val_M` + 2 місяці `Val_M`.
* **Суворий 2-годинний буфер `embargo`:** між `Train_M` і `Val_M`, а також між `Val_M` і початком тестового місяця $M$ вилучаються останні 2 години (`embargo_hours = 2`), що виключає будь-який перетин інтервалів цілі $[T, T+1\text{h})$ на межах сплітів.
* **Статус гіпотез у блоці Walk-Forward (`protocol_status`):**
  * `LightGBM (Set C) [WF Rolling 12m]` — **`primary hypothesis of the WF block (specified after viewing static Test results)`**.
  * `LightGBM (Set D) [WF Rolling 12m]` — `post-hoc exploratory` (перевірка детермінованого астрономічного й календарного розширення `Set D`).
  * `LightGBM (Set C) [WF Expanding]`, `LightGBM (Set B / C') [WF Rolling 12m]`, `LogReg (Set C) [WF Rolling 12m]` — `exploratory`.
* **Статичний орієнтир у таблиці WF (`Static Initial Train`):** використовується заморожена модель `models/lightgbm_adaptive.joblib` ($p^*=0.1290$) на Official та заморожена модель **`models/volunteer_lightgbm_adaptive_fixed_d.joblib`** ($p^*=0.1131$, навчена і оцінена строго на каузальній сітці `naive_fixed_D`) на Volunteer.

### 4.2. Інтерпретація Walk-Forward, порівняння `LogReg Static проти LGBM WF` та узгодженість гіпотез
1. **Чому у таблиці виділено рядок `LogReg Static проти LGBM WF (Set C: LGBM_WF − LogReg_Static)`:**
   * На **Official** помісячний `LightGBM (Set C) [WF Rolling 12m]` домінує над усіма статичними та лінійними альтернативами, випереджаючи `LogReg Static` на **$\Delta\text{PR-AUC} = +0.1031 \ [+0.0944, +0.1120]$** на повному Test та на **$+0.1245 \ [+0.1030, +0.1479]$** на останніх 60 днях.
   * Проте на **Volunteer (`naive_fixed_D`)** картина принципово інша: хоча помісячне донавчання `LightGBM (Set C) [WF Rolling 12m]` дає значущий приріст відносно статичного бустингу ($\Delta_{\text{WF − Static}} = +0.0147 \ [+0.0110, +0.0180]$ на повному Test та $+0.0430 \ [+0.0331, +0.0520]$ на останніх 60 днях) і перемагає `Adaptive 14-day` у `15/17` місяців, **називати `LightGBM` безумовно найкращою моделлю на Volunteer не можна**. Статична лінійна модель `LogReg (Set C) [Static Initial Train]`, яка монотонно екстраполює при зростанні `national_active_count`, зберігає вищий `PR-AUC` на повному Test (`0.4097` проти `0.4050`, $\Delta\text{PR-AUC} = -0.0046 \ [-0.0081, -0.0013]$) і статистично не відрізняється на останніх 60 днях (`0.5002` проти `0.4975`, $\Delta\text{PR-AUC} = -0.0027 \ [-0.0073, +0.0028]$). Перевага `LightGBM WF` над `LogReg Static` на Volunteer полягає лише у вищому $F_2$-Score ($\Delta F_2 = +0.0064 \ [+0.0044, +0.0083]$) та значно кращому калібруванні ймовірностей (`Brier = 0.1093` проти `0.2645`).
2. **Формулювання причинності (`узгоджується з` замість каузальних тверджень):**
   * Відновлення переваги повного набору `Set C` над скороченими `Set B` та `Set C'` на Official при переході до помісячного навчання ($\Delta_{\text{C − B}} = +0.0289 \ [+0.0243, +0.0338]$, $\Delta_{\text{C − C'}} = +0.0218 \ [+0.0176, +0.0260]$) та зрівняння `Set C WF` із `Set C' WF` на Volunteer (`0.4050` проти `0.4050` на повному Test і `0.4975` проти `0.4926` на 60 днях) **узгоджується з гіпотезою** про те, що просідання статичного `Set C` було пов'язане зі старінням фіксованих порогів розбиття дерев при 5-кратному зсуві `national_active_count` та зміні режиму логування після серпня 2025 р. Оскільки окремий інтервенційний тест для ізоляції причини не проводився, ми використовуємо виключно формулювання «узгоджується з».

### 4.3. Історія вирівнювання гіперпараметрів: Перший прогін WF проти вирівняного (`hyperparameter_alignment_history`)
Під час першого (докомітного) запуску [`src/models/run_walk_forward_experiment.py`](src/models/run_walk_forward_experiment.py) у функції `fit_fold_lightgbm` використовувалися інші гіперпараметри (`n_estimators=600, learning_rate=0.04, num_leaves=31, max_depth=6, min_child_samples=120, class_weight='balanced', eval_metric='average_precision'`), ніж у канонічному статичному скрипті [`src/models/train_models.py`](src/models/train_models.py) (`n_estimators=300, learning_rate=0.05, num_leaves=31, max_depth=-1, min_child_samples=50`, без `class_weight`, `eval_metric='binary_logloss'`), а як `Static Initial Train` на Volunteer підставлялася модель `volunteer_lightgbm_adaptive.joblib` (навчена на `naive_as_is`) поверх тестової сітки `naive_fixed_D`. ### 6.2. Методичні обмеження та застереження (Limitations)
1. **Чітке розмежування pre-specified та post-hoc гіпотез:** основним передреєстрованим порівнянням статичного блоку був `LightGBM (Set C)` проти `Adaptive 14-day Rolling`. Висновок про перевагу статичного `Set B` за PR-AUC, побудова `Set C'`, додавання астрономічного розширення `Set D`, а також постановка блоку `Walk-Forward Retraining` (`primary hypothesis of the WF block (specified after viewing static Test results)`) були сформульовані після перегляду результатів статичного Test.
2. **Множинні порівняння та залежність від `base_rate` у регіональному розрізі:** оцінка 24 областей у двох джерелах (`48` зрізів) має статус `exploratory`. Абсолютний `PR-AUC` всередині області механічно залежить від її `base_rate`, тому змістовними для міжрегіонального порівняння є лише парні внутрішньообласні різниці $\Delta\text{PR-AUC}$.
3. **Агрегація районів і громад після 01.08.2025 на Official:** реконструкція обласної тривоги як об'єднання інтервалів усіх районів області забезпечує неперервність часового ряду після реформи оповіщення, але зменшує кількість спокійних годин у прифронтових областях (зокрема у Донецькій та Дніпропетровській областях на Official, які тому позначені прапорцем `low_sample_flag = True`).
4. **Крайовий ефект 60-секундного фільтра мікро-тривог:** для тривоги, що почалася менш ніж за 60 секунд до моменту $T$ і ще триває в момент $T$, у ретроспективному очищенні факт того, чи перевищить її підсумкова тривалість 60 секунд, спирається на час відбою (проте частка таких годин на сітці становить менше ніж $0.05\%$).

### 6.3. 🔭 Future Work: Метеорологічні прогнозні ознаки (Open-Meteo Weather Forecasts)
У межах цього проєкту ми свідомо не включали метеорологічні змінні до навчальної матриці й залишили їхню інтеграцію для майбутніх досліджень (**Future Work**) з огляду на такі обмеження каузальності та історичної повноти архівів погоди:
1. **Проблема каузальності та історичної глибини архівів NWP (Open-Meteo `Historical Forecast` vs `Previous Runs`):**
   * Використання фактичних реаналітичних даних (`ERA5`) за годину $[T, T+1\text{h})$ створює прямий витік із майбутнього, а використання лише минулих фактичних вимірів станом на $T$ ігнорує синоптичний прогноз на наступну годину.
   * API склеєних прогонів **`Open-Meteo Historical Forecast API` (Single Runs)** об'єднує перші години послідовних запусків метеомоделей і не дозволяє строго відтворити стан прогнозу з урахуванням реальної затримки публікації прогону (`model availability lag` 3–6 годин після ініціалізації `00z/06z/12z/18z`).
   * Водночас каузальний архів **`Open-Meteo Previous Runs API`** має неповне історичне покриття для раннього періоду повномасштабного вторгнення (`2022–02.2024`: більшість серій доступні лише з березня 2024 р. або вересня 2025 р.), що не дозволяє побудувати однорідний безпропускний ряд на всьому періоді `Train` (`2022-03` – `2024-04`).
2. **Явне маркування припущень (Assumptions Disclosure):**
   * **Оцінка очікуваного ефекту на метрики є припущенням (assumption):** гіпотеза про те, що додавання каузальних прогнозів швидкості/поривів вітру на висоті 80–120 м, низької хмарності, опадів та видимості може забезпечити додатковий приріст порядку $\Delta\text{PR-AUC} \approx +0.005..+0.015$ у періоди переважання дронових атак, є **неперевіреним припущенням**, оскільки відповідний експеримент у цьому репозиторії не проводився.
   * **Фізичні аргументи щодо типів озброєння та районів пуску є припущеннями (domain assumptions):** твердження про те, що сильний вітер і обледеніння суттєво обмежують польоти ударних БпЛА типу *Shahed*, тоді як балістичні й крилаті ракети слабо залежать від приземної погоди в області-цілі (або залежать від метеоумов у районах пуску та акваторіях Чорного/Каспійського морів), є **предметними припущеннями**, які потребують окремої емпіричної верифікації на каузальних архівах NWP з урахуванням затримки публікації прогонів.

## 🚀 7. Швидкий старт (Quickstart)

### 1. Клонування та встановлення залежностей
```bash
git clone https://github.com/Yaroo-a/ukrainian-air-raid-sirens-analysis.git
cd ukrainian-air-raid-sirens-analysis
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### 2. Повний відтворюваний запуск усього пайплайну з нуля (`bash run_all.sh`)
Скрипт [`run_all.sh`](run_all.sh) послідовно виконує всі 9 етапів проєкту (очищення Official і Volunteer, RQ1–RQ3, генерацію Feature Store, статичне навчання, Walk-Forward Retraining, регіональний розріз по 24 областях, автотести та виконання всіх 5 Jupyter Notebooks):
```bash
bash run_all.sh
```
Або покроково:
```bash
# [1/9] Етап 1 (Official): Очищення, циклічність (RQ1), кластери (RQ2 + Train-only) та крос-кореляції (RQ3)
python src/data/cleaner.py
python src/features/cyclicity.py
python src/features/clustering.py
python src/features/propagation.py

# [2/9–3/9] Етап 2 (Official): Feature Store, зсув ознак, бейзлайни, статичні моделі (A, B, C, C') та оцінка на Test
python src/features/feature_store.py
python src/features/analyze_feature_shift.py
python src/models/baselines.py
python src/models/train_models.py
python src/models/evaluate_test.py

# [4/9–5/9] Незалежна верифікація на Volunteer (3 політики naive: as_is, drop_naive, fixed_D) та зведені порівняння
python src/models/run_volunteer_pipeline.py
python src/models/compare_datasets.py

# [6/9–7/9] Помісячний Walk-Forward Retraining (Rolling 12m & Expanding) та регіональний розріз по 24 областях
python src/models/run_walk_forward_experiment.py
python src/models/analyze_walk_forward_regional.py

# [8/9] Перевірка цілісності всіх 33 графіків, таблиць та 5-рівневий автотест каузальної інваріантності
python tests/verify_pipeline.py
python tests/test_leakage_invariance.py
```

### 3. Дослідницькі Jupyter Notebooks
* [`notebooks/01_data_profiling_and_cleaning.ipynb`](notebooks/01_data_profiling_and_cleaning.ipynb) — профілювання сирих даних Official і Volunteer, аудит дублікатів, дедуплікація та агрегація інтервалів.
* [`notebooks/02_rq1_temporal_cyclicity.ipynb`](notebooks/02_rq1_temporal_cyclicity.ipynb) — тижневі та добові ритми, частка нічних тривог і тест Краскела-Волліса на обох джерелах.
* [`notebooks/03_rq2_regional_clustering.ipynb`](notebooks/03_rq2_regional_clustering.ipynb) — описова ієрархічна кластеризація (RQ2) проти ізольованих Train-only кластерів для ML.
* [`notebooks/04_rq3_spatial_propagation_routes.ipynb`](notebooks/04_rq3_spatial_propagation_routes.ipynb) — крос-кореляції та часові затримки між 49 парами сусідніх областей ($\rho = 0.960$ між джерелами).
* [`notebooks/05_ml_forecasting_experiment.ipynb`](notebooks/05_ml_forecasting_experiment.ipynb) — статичний ML-бенчмарк, аналіз зсуву ознак, чутливість до `naive`, помісячний Walk-Forward Retraining, історія вирівнювання гіперпараметрів та регіональний розріз по 24 областях.
